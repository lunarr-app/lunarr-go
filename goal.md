# Playback Architecture Goal: FFmpeg Playback, NodeAV Probe

Replace Lunarr's current non-direct playback/transcode architecture with a Jellyfin-like FFmpeg CLI design, while keeping NodeAV for probe-oriented media inspection.

## Current Direction

Keep NodeAV for probe-style tasks such as media metadata, stream inspection, codec detection, duration detection, and other analysis workflows where its higher-level API is useful.

Use direct FFmpeg CLI for playback and streaming whenever the file cannot direct play in the browser. That includes HLS remux, HLS transcode, segment generation, seek restarts, local file input, and SFTP-backed input through Lunarr's private localhost range proxy.

## Goal Statement

Use NodeAV where it is strongest: probing media, reading metadata, inspecting streams, discovering codecs/duration, and supporting thumbnail or library-analysis workflows.

Use direct FFmpeg CLI process management where correctness matters most for playback: HLS remux, HLS transcode, segment generation, seek restarts, process lifecycle, stderr/error reporting, local media input, and SFTP-backed media input through Lunarr's private range proxy.

Direct play remains the fastest path when the browser can already play the file. Every non-direct stream should eventually be generated by FFmpeg CLI rather than NodeAV.

## Architecture Decision

Use the right tool for each layer:

- Keep NodeAV for probe-style work: media probing, metadata extraction, stream inspection, duration/codec discovery, and thumbnail-oriented workflows where its higher-level API is useful.
- Use direct FFmpeg CLI process management for all non-direct playback and streaming: HLS remux, HLS transcode, segment generation, seek restarts, stderr reporting, and process lifecycle.
- Keep direct play as the fast path for media the browser can already play without remuxing or transcoding.
- Do not use NodeAV as the user-facing HLS segment generator after this migration.

## Objective

Keep direct play for compatible media, but move all non-direct playback generation to direct FFmpeg CLI process management. FFmpeg should produce HLS playlists and segments for remux/transcode playback, while Lunarr manages sessions, authorization, progress, cleanup, and source access.

NodeAV should stay in the stack for probe-oriented work where its higher-level API is useful: media probing, metadata extraction, stream inspection, and possibly thumbnails. It should not remain responsible for user-facing HLS segment generation once the migration is complete.

## Scope

- Keep direct play unchanged for browser-compatible local media.
- Use FFmpeg CLI as the primary and only backend for HLS remux/transcode playback.
- Retire NodeAV from playback segment generation.
- Keep NodeAV for non-playback tasks where it remains useful, such as probing, metadata extraction, and possibly thumbnails.
- Support local files and SFTP media.
- Feed FFmpeg through a private, seekable, localhost HTTP range proxy instead of exposing raw SFTP credentials.
- Use short-lived internal tokens bound to a playback session for proxy access.
- Support `HEAD` and ranged `GET` requests in the internal input proxy.
- Translate proxy range requests to local file reads or SFTP range reads.
- Maintain one stable playback session per user/file/start/mode.
- On seek, cancel the old FFmpeg process and replace it with a new session/process at the target timestamp.
- Let FFmpeg handle HLS playlist and segment timing instead of custom NodeAV request-window generation.
- Serve FFmpeg-generated HLS playlists and segments through authenticated Lunarr routes.
- Keep robust cleanup for processes, temporary files, abandoned sessions, and stale HLS artifacts.

## Migration Notes

- Local non-direct playback moved to FFmpeg CLI first.
- SFTP non-direct playback should go through the private localhost range proxy and FFmpeg CLI, not NodeAV segment generation.
- The default non-direct playback backend should route both local and SFTP media through FFmpeg CLI.
- Do not remove NodeAV probing paths as part of the playback backend replacement.

## Jellyfin Reference

Consult Jellyfin docs and source as needed for proven behavior around:

- Direct play vs direct stream/remux vs transcode decisions.
- FFmpeg command construction.
- HLS segment generation.
- Seek/restart behavior.
- Playback session lifecycle.
- Transcode cleanup and cancellation.
- Client capability handling.

The goal is not to copy Jellyfin code directly, but to mirror the architecture and operational behavior closely enough that Lunarr playback feels stable, predictable, and seek-friendly.

## Expected Outcome

Playback should behave much closer to Jellyfin/Plex:

- Direct-compatible files start quickly without transcoding.
- Unsupported files start through FFmpeg-generated HLS.
- SFTP playback works without full-file staging.
- Seeks do not create duplicate active transcode jobs.
- Segment timing and playback progress remain correct.
- Failures are visible through clear FFmpeg stderr logs and session errors.
- Jobs show meaningful active playback work, not duplicated stale sessions.
